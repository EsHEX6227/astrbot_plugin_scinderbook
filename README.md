## 它是什么

一个 **两段式词条注入** 插件：词条文件里第一行写检索词，其余写正文；插件用**本地关键词索引**决定命中哪几条，然后**只把正文**注入这一轮上下文。

- 不调用 embedding、不发一次外部请求，索引和召回全在本机
- 检索词永远不会出现在模型看到的上下文里
- 命中才注入，没命中就和没装这个插件一样
- 注入走对话尾部临时片段，不破坏系统提示词前缀（KV Cache 友好）
- 自带管理页：逐个查看词条、标出格式有问题的地方、直接在页面里改

## 和已有方案的关系（先把话说清楚）

这套做法的**技术本身不新**，本插件是把它落成 AstrBot 里一个最小实现：

| 组成 | 出处 |
|---|---|
| 关键词触发词条、命中注入正文 | SillyTavern / NovelAI 的 **World Info（世界书）**；Character Card V2 的 `character_book` 也是同一套语义 |
| 索引字段与展示字段分离 | 搜索引擎几十年的常规做法（Elasticsearch 的 index/display 字段） |
| BM25 + 倒排索引 | 1970 年代经典算法，FTS5 是 SQLite 自带实现 |
| 中文分词 | [jieba](https://github.com/fxsjy/jieba) |
| AstrBot 内的世界书式注入 | [QuillPlus 羽笔](https://github.com/Nana7mi0721/astrbot_plugin_quillplus) 已经在做 |

**这个插件新在哪**：它只做这一件事——不带角色卡、素材库、状态栏，不引入第二个模型服务；只用一个 SQLite 文件做索引，注入位置选在对话尾部，因此不会像往 system prompt 里拼东西那样打断前缀缓存。如果你要的是一整套 RP 增强，请用 QuillPlus；如果你只想让「词表 + 正文」这种词条被准确召回，用这个。

## 为什么需要它

很多人的知识库是这样写的：

```md
# Kn视力

看 观看 视觉 视力 看见 视
作为大语言模型的电子猫娘，你默认没有视觉能力。
当且仅当有具体通知或者你能调用视觉工具时，你可以使用「我看见……」这类表达。
```

第一行是检索词，下面是正文。但在**向量检索**里，这两者被拼成一个 chunk 一起做 embedding：

- 检索词稀释了正文语义，向量落在两者之间的某个位置
- 「看 观看 视觉 视力 看见 视」这种词表被当成正文的一部分参与相似度
- 分数被压平：实测 nomic-embed-text 上，「消息抖动是什么」这条查询最相似的是「Kn触觉」（0.754），正确的条目根本进不了前三

ScinderBook 的解法是把两件事彻底分开：

```
词条目录 (.md)
   ├── 检索词 ──► 本地索引（jieba + FTS5/BM25 + 精确词加权）──► 命中
   └── 正文   ──► 注入上下文（只有条目名 + 正文）
```

## 工作原理

```
启动 / /kwb reload
   └── 递归扫描 vault_dir 下的 .md
         └── 解析：标题 → 条目名；标题后第一行 → 检索词；其余 → 正文
               └── 过滤：缺召回词或正文为空的跳过（文件保留，管理页标红，改好自动恢复）
                     └── 写入 SQLite：entries 表 + FTS5 倒排（tokens 由 jieba 切分）

每轮 LLM 请求（on_llm_request）
   └── 拿本轮用户消息 → 分词 → FTS5 MATCH 召回 top 50
         └── 打分：-bm25 + 精确检索词命中次数 × 3
               └── 取 top_n、按 max_chars 截断、并入常驻词条
                     └── 以临时片段注入对话尾部（可切回 system_prompt）
```

## 词条格式

### 极简格式（推荐）

```md
# Kn视力

看 观看 视觉 视力 看见 视
作为大语言模型的电子猫娘，你默认没有视觉能力。
当且仅当有具体通知或者你能调用视觉工具时，你可以使用「我看见……」这类表达。
```

### YAML frontmatter（需要常驻，或正文开头本身很特殊）

```md
---
keywords: [署名, 落款, 签名]
always: true
---

# Kn署名

落款写 YuJie.ctr，位置在正文末尾。
```

### 识别规则

| 情况 | 处理 |
|---|---|
| 有 frontmatter 且含 `keywords` / `aliases` / `alias` / `keys` | 用它作为检索词，正文不再拆 |
| `keyword_mode = frontmatter_only` | 只认 frontmatter，其余全算正文 |
| 无 frontmatter | 标题后第一行若"像词表"就当检索词 |
| 什么也没识别到 | 整篇都是正文，靠正文分词召回（也能用，只是精度差些） |

「像词表」的判定：不含 `。！？，、；：…—` 这类句子标点、至少 2 个词、每个词不超过 24 字、整行不超过 240 字。`[[双链]]`、引号会被剥掉，只留关键词。

## 安装

```bash
cd AstrBot/data/plugins
git clone <本仓库地址> astrbot_plugin_scinderbook
```

重启 AstrBot → 插件页启用 → 插件配置里填 `vault_dir` → 回到插件页打开「词条管理」。

> **关于插件市场**：AstrBot 的插件市场不会自动扫描 GitHub 仓库。仪表盘拉的是 `AstrBotDevs/AstrBot_Plugins_Collection` 里的 `plugin_cache_original.json`，要进去得走官方提交入口（该仓库 README 指向 <https://cloud.astrbot.app/>），审核合并后市场才会显示。在那之前只能 `git clone` 手动装，或者用仪表盘「插件市场 → 自定义源」指向自己的清单。

依赖：`jieba`（可选）。装了按词切分，没装自动退化成「中文二元组」切分，能跑但召回会差一些。AstrBot 自带的知识库本来就依赖 jieba，多数环境无需额外安装。

需要 SQLite 带 FTS5（官方 Python 发行版默认都有）。

## 管理页（WebUI，v0.3.0 起）

插件自带一个管理页，不用改配置也不用命令行：仪表盘 → 插件 → ScinderBook → **词条管理**（页面目录 `pages/console`）。

页面分两块：

- **左侧：条目总览 + 分类**。按 `vault_dir` 下的子文件夹自动生成目录树，二级文件夹照旧嵌套；点一下展开、再点收起，默认全是收起的。点某个文件夹等于把「当前位置」设成它，之后新建或导入都落到这里。
- **右侧：从上到下三栏**——**标题 → 召回词 → 内容**。左栏点任一标题，这三块立刻变成该词条的编辑区：标题和常驻开关在最上面，召回词逐个 chip 可删、「从正文提取候选」一键抽词，内容是一整块可直接改的 textarea，底部是保存/撤销/删除。

**导入**：把 `.md` 拖到页面上任意位置（右上角「导入 .md」也能选文件）就会读到当前目录，按「标题 + 召回词 + 正文」重新排版后落盘。

- **格式不对的也照收**，只是标成「不可召回」：目录里名字标红，但不参与检索、也不会被注入
- 内容不会被吞：比如缺召回词的文件，`# 标题` 以下的整篇内容都留在「内容」栏里，你自己把词表那行剪到「召回词」栏就行
- 具体原因不刷屏，**点开那条才显示**；改好保存、通过检查后，下一次重建就会开始参与召回
- 只有「不是 `.md` / 文件是空的 / 写不进去」才退回
- 同名文件自动加 `-2`、`-3` 后缀，不覆盖已有词条
- 导入完自动重建索引并打开第一条

**什么算「不可召回」**（文件在、内容在，只是不进索引）：

| 情况 | 为什么 |
|---|---|
| 手动禁用（目录里点「禁用」） | 你自己说这条先别用；文件不动、正文不动，点「启用」随时恢复 |
| 没有召回词，**且不是常驻** | 没有任何入口能命中它，只能靠正文分词瞎撞，等于不可控 |
| 正文为空 | 命中了也没内容可注入 |

四个例外/说明：

- **禁用是最高优先级**：禁用的条目既不召回也不注入（常驻也照样停掉），在目录里显示为灰色删除线。
- **常驻词条不需要召回词**：它每轮都被无条件注入，所以「没有召回词」对它不算问题（也就不会标红）。常驻有两种写法，效果一样：管理页勾「常驻注入」（写进 md 的 `always: true`），或者插件配置里的 `always_files` 列表（写 `Kn背景`、`Kn背景.md`、`sub/Kn背景.md` 都认）。
- 缺 `# 标题`、文件名与条目名不一致这类问题只影响展示，**不阻断**召回。
- `/kwb stats` 会分别显示「已禁用」和「不可召回」的条数。

禁用和常驻都写在 md 的 frontmatter 里（`disabled: true` / `always: true`），所以它们跟文件走，用 Obsidian 打开也能看见。

**分类**：左侧目录按 `vault_dir` 的真实子文件夹生成，空文件夹也会显示；点「＋ 文件夹」可以自己建（支持 `名/子名` 建多级），建完自动定位过去，新建词条和拖拽导入都会落到这个位置。注意分类只影响组织方式，不影响召回规则。

其它细节：

- **格式问题会自动标出**：标题前的圆点分红/黄/灰，列表上方有「仅看问题」筛选，点开就能看到原因
  - `error`（标红 + 不参与召回）：文件读不出来、正文为空、没有召回词
  - `warn`（能跑但要看一眼）：正文超过单轮注入上限、frontmatter 标题与正文标题不一致
  - `info`（仅提示）：缺 `# 标题`（条目名退回文件名）、文件名与条目名不一致
- **保存按规范重排**：`# 标题` → 召回词行 → 空行 → 正文；勾了「常驻注入」就写成 frontmatter 的 `always: true`
- **md 仍是唯一真源**：页面只是把它写回规范格式，索引和向量都是可重建的缓存，删掉重扫不影响内容
- **只碰目录内的 `.md`**：路径必须是 `vault_dir` 下的相对路径且以 `.md` 结尾，`..`、绝对路径、无扩展名一律拒绝
- 在 Obsidian 里改完上传，点右上角「重新扫描」即可刷新；保存 / 新建 / 删除 / 导入后会自动重建
- **顶栏「检测嵌入」**：真的调一次 `get_embedding("ping")`（8 秒超时），成功显示「可用 · 维度 · 耗时」，失败给出可读原因（没填 `embedding_provider_id` / 提供商里找不到 / 连接被拒 / 超时 / 空向量）。用来确认 ollama 之类的嵌入服务当前有没有起来，不用开终端；它不会写库、不改配置

> 实现注记：插件页面跑在仪表盘的 sandbox iframe 里（`allow-scripts allow-forms allow-downloads`，**没有** `allow-same-origin`），所以页面拿不到 cookie，`prompt()` / `confirm()` 也会被浏览器静默拦掉。因此本页所有请求都走宿主的 `AstrBotPluginPage.apiGet/apiPost` 桥接，所有弹窗都是页内自绘的，没有用原生对话框。

页面标题与插件简介的语言由 `.astrbot-plugin/i18n/` 下的文件决定（`zh-CN.json` / `en-US.json`）。

## 语义兜底（可选，v0.2.0 起）

默认是纯关键词。如果你希望「意思相近但用词不同」也能召回，可以打开语义兜底：

```text
semantic_enabled: true
embedding_provider_id: ollama_bge_m3      # AstrBot 提供商里已有的嵌入模型
semantic_min_sim: 0.45                    # 余弦阈值
semantic_top_n: 3                         # 最多补几条
```

**关键设计：embedding 只吃正文，不吃检索词。** 这正是它和原生向量知识库的区别——原生 KB 把「看 观看 视觉 视力 看见 视」和正文拼成一个 chunk 一起向量化，词表会稀释语义；这里检索词只留在倒排索引里，向量只描述正文。

融合策略是**关键词优先**：

```
词法最高分 < semantic_override_score（默认 3.0）
    → 认为词法只是勉强命中，丢掉词法，改用向量
词法分数够高
    → 词法优先，向量只在没占满 top_n 时补位
两个都没结果
    → 不注入
```

实测（本地 bge-m3，27 条词条）：查「被人摸是什么感觉」时词法只得到 2.1 分的噪音命中，向量给出 Kn触觉 0.604 —— 这种情况就是靠 `semantic_override_score` 让位的。

所以打开兜底不会让精确命中变差，只是补位。代价是每次查询多一次本地 embedding 调用（用 ollama 就是本地、免费），重建索引时要为每条正文算一次向量。

本地 bge-m3（1024 维）上，27 条词条的向量构建在 1 秒级；查询延迟取决于嵌入模型本身。
## 设计取舍

**默认没有语义泛化。** 纯关键词模式下，查「视力」不会命中只写了「眼睛」的条目——要么把同义词写进检索词行，要么打开上面的语义兜底。这是它精确、可解释、零成本的原因，也是它的边界；语义兜底是补位，不改变「关键词优先」的排序。

**不注入检索词。** 词表只进索引，不进上下文。好处是模型看到的每条都是干净的正文；代价是模型不知道自己是被哪个词命中的（它可以自己看用户说了什么）。

**尾部注入。** 默认 `extra_user_content_parts` 临时片段，不写历史、不进 system prompt，因此不会让前缀变化导致整段历史缓存失效。这是给 DeepSeek 这类前缀缓存模型准备的。

**全量重建。** 几百条词条的目录重建在一秒内，不做增量索引，省掉一堆一致性 bug。

## FAQ

**Q：词条很多会不会慢？**
索引是 SQLite FTS5，万级词条也是毫秒级。瓶颈在启动时扫盘一次。

**Q：为什么不用 embedding？本地也有 ollama。**
可以，但那就变成向量检索了，回到「词表稀释语义」的老问题。这个插件的定位就是不依赖任何模型。

**Q：中文以外能用吗？**
能。非中文按空格/字符边界切，FTS5 的 unicode61 分词器处理拉丁文字没问题；只是混合中英时召回质量取决于 jieba。

**Q：和 AstrBot 原生知识库冲突吗？**
不冲突。原生知识库的自动注入照常，ScinderBook 只是额外补一段词条正文。如果两套都开、又都命中同一条，建议把该条从其中一边删掉。

**Q：常驻词条会不会把上下文吃满？**
`max_chars` 是硬上限，常驻条目同样受它约束。放太多会挤掉命中条目，建议常驻只放一两条全局基调。常驻条目**不需要召回词**，也不会进倒排索引（不会被关键词召回抢 `top_n` 的位置）。

**Q：ollama 跑完 embedding 之后，能关掉 ollama 继续用语义兜底吗？**
不能——**稠密召回必须现算查询向量**。词条的向量确实缓存在 SQLite 里（`embeddings` 表），但每次查询都要把用户这句话也 embed 一次才能比余弦，这一步调不到嵌入接口就做不了。

至于「AstrBot 原生知识库好像不开 ollama 也能召回」：那是 **BM25 稀疏那半在干活**。原生 KB 的检索是混合的（稠密向量 + FTS5/BM25 稀疏 → RRF 融合 → 可选 rerank），`_dense_retrieve` 里每条知识库是独立 `try/except`，嵌入接口挂了只会 `logger.error` 然后跳过稠密，稀疏照样返回结果。向量那半照样没工作，只是你没察觉。

ScinderBook 的语义兜底是纯稠密，所以：

- ollama 关着 → `get_embedding` 失败 → 该轮语义兜底自动跳过（只记一条错误日志，不影响关键词召回和注入，不会崩）
- 纯关键词链路本身就是「不依赖模型」的那一半，随时可用
- 换嵌入模型或维度变了，会整表重算（重建索引时一起做）

## AI 生成声明

这个仓库是 AI 生成项目，不是纯人工手写：

- **AI 负责**：`main.py`、`scinderbook/` 下的核心实现、`web_api.py` 与管理页 `pages/console/index.html`、单测、README 与 CHANGELOG 的初稿
- **人类负责**：需求定义、检索策略取舍（为什么不用 embedding）、评审与发布
- **怎么复核**：
  1. 跑 `python tests/test_entry.py`、`tests/test_index.py`、`tests/test_semantic.py`、`tests/test_manager.py`，四套都过再往下
  2. 拿自己的词条目录跑 `/kwb test <关键词>`，确认命中的条目符合预期
  3. 先只在一个会话里启用，观察几轮注入结果（`debug: true` 会打印命中详情）
  4. 管理页的保存会**重写 md 文件**，第一次用请先备份词条目录，或者先只读不保存看一眼体检结果
- **已知风险**：AI 容易写出「测试能过但边界不对」的代码，比如过长的检索词行、含句子标点的词条、常驻条目挤占 `max_chars`。这些情况单测覆盖了主要分支，但不保证穷尽。
